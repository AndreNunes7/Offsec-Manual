# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

**OffSec Manual** is a personal, single-user *guided* playbook for offensive security work (Pentest, Bug Bounty, Web Application assessments), organized around PTES, OWASP WSTG/Top 10, NIST SP 800-115, MITRE ATT&CK and CWE. It is a single static HTML file — `index.html` — with all CSS and JS embedded inline. There is no backend, no build step, no package manager, and no external dependencies. It is meant to be opened directly or served as a static file; all data (engagements, checklist progress, notes, target variables) lives in the browser's `localStorage`.

Do not split this into separate `.css`/`.js` files or introduce a bundler/framework — staying a single dependency-free file is a deliberate, explicit requirement (same convention as the sibling project `diario-chamados`), not an oversight.

**This tool is local-only by design.** It is not meant to be deployed publicly — it documents real assessment methodology and, once used, will contain real engagement names/targets/notes in the user's own browser storage. Never suggest hosting it on a public URL as a default action. **`pi-agent/` is the one deliberate exception to "no backend"** — see the "Pi Agent" section below — and it stays LAN-only by the same logic: never suggest binding it to `0.0.0.0` or exposing it past a trusted home/lab network.

**v2 design note.** The first version organized content as a browsable domain tree (Web/AD/Linux/...) with every module expanded into 9 always-visible cards, plus a large set of stub placeholder pages for unwritten content. User testing showed this was dense, hard to scan, and didn't feel like a *guide* — just a wiki. v2 rebuilt around a phase-based guided flow, a **collapsed-by-default reference layer** with an always-visible checklist, and a **live variable substitution engine** for commands. All unwritten (stub) content was deleted rather than kept as placeholders — see "Adding a new step" for how to reintroduce a topic later.

**v3 design note.** v2 exposed the 7 PTES phases as the only navigation but never used the `scopes` field the steps already carried, so every engagement looked the same and two phases (Scanning, Reporting) rendered blank. v3 turns the flow into a **per-scope wizard**: the engagement now has a `scope` (`web` / `interno` / `externo` / `bug-bounty` / `api`, the ids of `SCOPES`), and the sidebar becomes a **numbered stepper** whose steps are *Setup* followed by only the PTES phases that actually have a step for that scope. `SCOPES` is the source of truth for both the wizard shape and the setup form; `wizardSteps(scopeId)` derives the ordered `[{kind:'setup'}, {kind:'phase',...}]` list used by navigation, stepper, validation and progress. v3 also fixed two live bugs (dead `.var-field` handler that killed variable substitution, and `var(--domain-*)` vs the `--dom-*` tokens) and wrote real content for Scanning and Reporting. v3.1 flipped the per-step disclosure pattern (commands/tools always visible, only narrative context behind a toggle) and made the session vars bar collapsed-by-default — see "Disclosure pattern" and "Session vars bar" below.

**v4 design note.** The wizard guided *doing* the work but produced no deliverable, and the checklist was a blunt boolean despite the app's own premise that "a real pentest isn't linear." v4 adds: a **tri-state checklist** (`done`/`na`/pending) with per-item evidence, so an inapplicable item can be marked out without lying about coverage; a **global findings list** (`#/achados`) with severity/CWE/CVSS/evidence/recommendation, addable from any module via "+ Registrar achado deste módulo"; a **generated report** (`#/relatorio`) that renders the findings as a document and exports to Markdown or a clean print stylesheet; and productivity tools on the phase page (copy every command in the phase at once, hide completed modules) plus a **progress ring** replacing the plain percentage badge. Three new API modules (`api-recon`, `api-authz`, `api-auth`) fill the Information Gathering and Vulnerability Analysis phases that were previously empty for that scope. None of this added a 4th localStorage key — `findings` and `evidence` live inside `state[engagementId]` exactly like `vars`/`setup`, so export/import cover them automatically.

**v7 design note.** Visual-only versions v5 and v6 (see Visual design system below) never got their own entry here since neither touched data model or features; v7 is the next entry in this shared version timeline (matching the v3.1 cross-reference below) and covers both a new feature and a round of cosmetic polish shipped together. v4 made the app produce a report, but every finding still had to be typed by hand. v7 adds a **companion automation layer, `pi-agent/`** (see the "Pi Agent" section below) — a small standalone Python HTTP service, meant to run on a Raspberry Pi or any LAN machine with recon/vuln tools installed, that `index.html` can call to trigger real nmap/subfinder/httpx/nuclei runs and pull back structured results. This is the one deliberate, documented exception to "no backend" — `index.html` still works standalone with zero setup, the agent only matters if you configure it. Results land as **draft findings** (`status: 'rascunho'`, new first entry in `FINDING_STATUS`) so automated output never reaches the polished report without a human reviewing it first. v7 also shipped three small, independent visual improvements — see the "v7" note under Visual design system — and a favicon.

**v9 design note.** A round of flow/UX fixes and finding-quality work, all app-side (no `pi-agent/` changes). Four things the user hit while running the tool for real: (1) the Automação page **asked to configure the agent on every new engagement** — because the Pi connection was stored per-engagement despite being the same physical box; v9 moves it to a **global** `offsecManual.agent` key (with a one-time migration lifting any legacy per-engagement config up), so it's configured once for all engagements (this made the schema 4 keys — see Persistence). (2) In the engagement modal, **clicking "Usar" on an engagement didn't open it** — the switch happened silently behind the still-open modal; fixed by closing the modal + navigating + toasting. (3) The **agent's auto-findings were low-quality** — no CWE/recommendation, no dedup, one noisy `info` finding per port/subdomain/header; `agentHandleJobDone` now fills CWE/recommendation from `AGENT_TOOL_DEFS`, deduplicates, and aggregates recon noise into one finding per job, and `sourceTool` is finally shown in the UI + report (see the Pi Agent section's v8 result-shape note, extended for v9). (4) **Automation was fiddly to drive** — v9 puts the target input directly on the Automação page and adds a post-run "review drafts" CTA. A follow-up in the same v9 round: the user found the standalone `#/achados` page and its sidebar link redundant with Automação (achados are mostly what the pipeline produces) and asked for them merged, plus the finding cards themselves had grown "muito feio" (always-fully-expanded forms) now that automated findings carry long evidence/recommendation text — see "Achados & Relatório" below for the merge and the new collapsible card. None of this touched the parsers or the agent backend, so no re-deploy to the Pi was needed.

**v8 design note.** The Automação console from v7 drew user pushback on two fronts: the stage cards ("Recon", "Information Gathering"...) looked like an arbitrary bucket list rather than a cited methodology, even though they already were `PHASES` in PTES order, and the "Rodar tudo" confirmation checkbox was flagged as friction worth removing — a check of `agentStartScan()` confirmed the frontend already hardcoded `confirm: true` on every job regardless of the checkbox, so the checkbox gated nothing real and was safe to drop (the actual gate is server-side in `agent.py`). v8 also widens the automatable surface into the **Exploitation** PTES phase for the first time: `sqlmap` (SQL injection) and `dalfox` (XSS) join `AGENT_TOOL_DEFS`, both defaulting to conservative scan profiles since — unlike the rest of the pipeline — they perform active injection attempts, not passive/read-only recon. CSRF deliberately did **not** get a dedicated pipeline tool: a real CSRF finding needs an authenticated PoC (see the `wstg-sess` step's own content), which a stateless one-shot CLI scanner can't produce — the automatable slice of that (cookie `SameSite`/security-header signal) was already covered by `oblivion-webvuln` and just got called out more explicitly in its description. See the "Pi Agent" section and its v8 notes below for the full detail on the tag/index/checkbox changes.

**v10 design note.** A visual redefinition of the achados cards (Automação/`#/achados`), requested after v9's collapsible card still left findings hard to scan. Two real problems, not just polish: `SEVERITIES` (index.html) had `critico` and `alto` both pointing at `var(--stop)` — the two most severe levels were visually identical — and `medio` reused `var(--signal)`, the app's one interactive accent (reserved for "this is clickable" per Visual design system below), which is the wrong signal for a static chip. Fixed by giving severity its own categorical palette, `--sev-critical/--sev-high/--sev-medium/--sev-low/--sev-info` in `:root` (same "categorical, not semantic" bucket as `--dom-*`), and pointing `SEVERITIES[].color` at those instead. Three structural changes followed from actually using that palette: (1) `.severity-chip` became a filled pill (`color-mix` background/border off `--sev`) instead of a thin outline — too subtle to be the primary severity signal on a near-black ground; since `.severity-chip` is shared with `#/relatorio`, that page's chips pick up the same treatment automatically, no renderer changes needed there. (2) `achadosSectionHTML` now partitions findings into per-severity sections (`achadosSevSectionsHTML`, new) in `SEVERITIES` order instead of raw insertion order — mirrors the sort `renderRelatorio` already did, so achados finally reads "how many críticos do I have" at a glance instead of scrolling a flat list. (3) `findingCardHTML`'s collapsed header grew a **status badge** (`FINDING_STATUS[].color`, new field — aberto=ash, confirmado=go, reportado=signal; rascunho stays on `.finding-draft-tag` alone so it isn't shown twice) and moved to a two-row layout (`.finding-summary-main` chip+title, `.finding-summary-badges` wrapping below) because the old single-line header truncated the title at `max-width:46%` while competing with every badge for the same row. The expanded form got a matching pass — `.finding-grid` now has two `.finding-section-label` groups ("Classificação" / "Detalhes") instead of one flat 8-field grid — with no `data-field` attributes touched, so the existing input/select handlers needed no changes. Also added the missing `.finding-card-body[hidden] { display: block !important; }` print rule (same pattern as `.step-detail`/`.checklist-evidence`, see "CSS `[hidden]` gotcha") since printing Automação with collapsed cards previously lost their content. Scope was deliberately kept to the achados cards only — `renderRelatorio`/`buildReportMarkdown` structure is untouched.

**v11 design note.** v10's card-based achados redesign (better severity colors, status badge, grouping) shipped and the user tried it, then rejected the whole direction — not a request for more tuning, an explicit "não quero esse design" plus a structural ask: put achados on its own screen, separate from wherever the Pi Agent pipeline lives. **v12 design note.** v11's flat tabular list still didn't satisfy the user ("ainda não gostei"); this round is a full visual rebuild of `#/achados` into an inline **design system**, plus two concrete behavior asks. Critically, the user asked to "utilize bibliotecas como tailwind, bootstrap" — which directly conflicts with this repo's load-bearing "single file, no build, no external dependencies, offline/local-only" rule. Rather than silently comply (a CDN framework breaks the tool offline, which matters for pentest use in isolated networks) or silently refuse, this was surfaced as an explicit choice; the user picked **"design system inline"** — deliver the modern framework *look* with hand-written inline CSS/JS, keeping the single-file/offline guarantee. So: no Tailwind/Bootstrap, but a much richer `.ach-*` component layer. The three asks, all in `#/achados` only: (1) **collapsed by default** — `achadosRowHTML`'s `expanded` is now `expandedFindings[f.id] === true` (was: auto-open for drafts/untitled); freshly-created findings still open because the `data-finding-new`/`data-add-finding` handlers now set `expandedFindings[id]=true`+`editingFindings[id]=true` before navigating. (2) **expand → formatted read view** (not a raw form): `achadosReadHTML` renders a spec grid (severidade/status/CVSS/CWE/ativo/detectado-por) + prose blocks; an **"Editar" button** (`data-finding-edit`, new `editingFindings` in-memory map) flips to `achadosEditHTML` (the same fields as before). (3) **better content rendering** — `formatEvidenceHTML` detects token-like multi-line evidence (directory/host/subdomain lists, the "resultados dos diretórios encontrados" the user called out) and renders a **structured results table** with per-line index + color-coded HTTP status badge (2xx green / 3xx amber / 4xx-5xx red), while request/response or prose falls back to a monospace `<pre>` (detection guards against misclassifying request/response — requires 3+ lines, no blank line, every line a whitespace-free token). Also new: a **dashboard** (`achadosDashHTML`) with a proportional severity distribution bar + the clickable filter chips (moved off the shared `.severity-tally` onto a dedicated `.ach-chip`). See "Achados & Relatório" below for the full component/why breakdown. `SEVERITIES`/`FINDING_STATUS`/`.severity-chip` and the whole report/relatório renderer were left untouched.

**v17 design note.** The user's complaint was specifically about the *scanner's* output quality: "quando rodar o pentest automatizado... a ferramenta do python e todas as suas ferramentas do código, tragam um retorno melhorado" — i.e. fix it at the source (`pi-agent/`), not just re-skin the frontend's guesswork again. Two-sided change: (1) **`pi-agent/parsers.py`** — every one of the 11 parsers now attaches an optional `meta` dict of tool-specific structured fields to each result (`{host, port, protocol, service, product, version}` for nmap, `{statusCode, title, tech, webServer, contentLength}` for httpx, `{templateId, matcherName, tags}` for nuclei, `{parameter, type, payload}` for sqlmap, etc. — see the "Normalized result shape" note in "Pi Agent" below for the complete list). Purely additive: the existing `evidence` string is untouched (still what the Markdown report reads), `agent.py`/`jobs.py` needed zero changes (they already pass parser output straight through), and a parser that skips `meta` just means that tool's findings render exactly as before. Verified with a standalone smoke test exercising all 11 parsers against synthetic fixtures (not part of the repo — there's no test suite here, see Development below). (2) **`index.html`** — `agentHandleJobDone` now carries that `meta` through into the finding (`items` array for aggregated recon findings, one entry per port/host/path; singular `meta` for individual vuln findings), and the achados read view (`achadosEvidenceHTML`/`paItemsTableHTML`/`RESULT_COLUMNS`, plus `META_LABELS` feeding the `.ach-spec` grid) renders a **real HTML table with named columns** instead of `formatEvidenceHTML`'s v12 regex-guessing when that structure is present. Manual findings and any finding without `items`/`meta` (older scans, before this change) fall through to the exact v12 behavior unchanged. See "Achados & Relatório" and "Pi Agent" below for the full mechanism.

## Architecture

Everything lives inside one `<script>` IIFE at the bottom of `index.html`, organized in clearly commented sections in this order: **CONSTANTS** (`SCOPES`, `PHASES`, `DOMAIN_LABELS`, `VAR_FIELDS`) → **CONTENT DATA** (the `STEPS` array and `FRAMEWORKS` array — by far the largest block) → **STATE / PERSISTENCE** (incl. scope/setup helpers and the `wizardSteps`/`stepsForScope` derivation) → **ROUTER** → **HELPERS** → **VARIABLE SUBSTITUTION ENGINE** → **RENDER ENGINE** → **SEARCH** → **MODAL / TOAST** → **ENGAGEMENT MODAL** → **INIT**. The `<style>` block in `<head>` follows the same top-to-bottom order: tokens → reset → app shell → sidebar/stepper → main/session bar → phase header/domain filter → step list → wizard (progress/nav/setup/scope-picker/resumo) → modals/toast → responsive → print.

`SCOPES` is the first constant: each entry has `id`/`label`/`desc` plus a `vars` array (the subset of `VAR_FIELDS` keys that scope's session bar and setup show — with per-scope `label`/`placeholder`/`required` overrides) and an `intake` array (free-text engagement documentation, **not** command tokens). `getScope(id)` looks one up.

There is no virtual DOM: render functions rebuild `#content`'s subtree via `innerHTML` on every navigation *and* on every state mutation (checklist toggle, domain filter, details toggle). This app does **not** re-attach listeners after every render — instead, `content`, `varsBar`, `phase-nav`, and the modal bodies each get **one delegated listener** in `init()` (click/input, matched via `closest('[data-...]')`), so newly rendered HTML "just works" without any re-attach step. If you add a new interactive element inside rendered content, give it a `data-*` attribute and extend the existing delegated handler in `init()` — do not attach a listener directly to a rendered element, it will be destroyed on the next re-render.

**Exception — live variable substitution does not re-render.** Typing in a `data-var` input (session bar *or* the setup form) calls `setVar()` (persists immediately) and `updateAllCommandOutputs()`, which walks every `code[data-cmd-tpl]` currently in the DOM and rewrites its `innerHTML` in place via `commandToHTML()`. It deliberately does **not** call `render()` — a full re-render would rebuild the `<input>` elements and drop focus/cursor mid-keystroke. The session bar and the setup form both render `data-var` inputs for the same keys, so the handlers mirror the typed value into the twin input by hand instead of re-rendering. The same no-re-render rule applies to setup `data-setup` fields, the setup Avançar button (toggled via `syncSetupValidity()` touching classes/attributes directly), and the per-step notes `<textarea>` (`data-notes-step`, debounced save + status label).

## Information architecture — scope picks the track, phase orders it, domain filters within it

The original brief listed things that don't sit at the same level: engagement types (Pentest Externo/Interno...), technical domains (Web/AD/Linux...), and kill-chain phases (Recon/Privesc/...) as if they were siblings. v3's resolution, confirmed with the user:

- **Scope is the top level, chosen per engagement.** `SCOPES` ids (`web`/`interno`/`externo`/`bug-bounty`/`api`) live on `engagement.scope`. With no scope set, the router forces `#/escopo` (the scope picker). Changing scope reconfigures the whole track but never erases progress — a checklist for a step outside the new scope simply stops being counted and comes back if the scope does.
- **The wizard is Setup + the PTES phases that have content for the scope.** `PHASES` holds the 7 phases in order — **Information Gathering → Recon → Scanning → Vulnerability Analysis → Exploitation → Post-Exploitation → Reporting** (v13 reorder: Information Gathering leads, aligned with OWASP WSTG §1 where it is the first category; the rest follows PTES §3–§7). `PHASES` is the single source of truth for phase order — the sidebar stepper, `wizardSteps`, the Automação stage grid (`stageSectionHTML` via `PHASES.filter`) and `AGENT_TOOL_DEFS` all derive from it, so reordering `PHASES` (and keeping `AGENT_TOOL_DEFS` in the same sequence) reorders every surface at once; there is no second place that hardcodes phase order. `wizardSteps(scopeId)` returns `[{kind:'setup'}]` followed by only the phases where `stepsForScope(phaseId, scopeId)` is non-empty. An empty phase is never shown, so the numbered stepper (`01`…`0N`) differs per scope. Adding content to a currently-empty phase makes it appear automatically — no other change needed.
- **Domain (`ad` / `web` / `linux` / `general` / `api`) is metadata on a step, not a nav level.** `renderPhasePage()` filters by `stepsForScope()`, then derives which domains are present *within that filtered set* and renders them as filter chips — a chip only appears if a visible step has it. Domain identity is purely a colored dot + filter chip + chip color token (`--dom-*`).
- **Every step carries `scopes: [...]`** (which engagements it belongs to) **and a `phase`.** Web/API steps get whichever phase the technique most naturally maps to (e.g. Authentication → `exploitation`, Authorization/IDOR → `vuln-analysis`).
- **Only the Setup step blocks.** The scope's `required` vars must be filled before any phase opens (`setupComplete()` / `missingRequiredVars()`); phases themselves never block on checklist completion — a real pentest isn't linear.

## Content data model

`STEPS` is a **flat array**, no `parentId`, no category wrapper nodes — a step needs `id`, `domain`, `scopes`, `phase`, `title`, `shortDescription`, optional `methodology`/`oblivionTip`, and a `content` object. There is no `status`/stub concept: every step in `STEPS` is expected to have full `content`. `FRAMEWORKS` is a separate small array (name/desc/link) that only backs the standalone `#/metodologias` reference page.

```js
{
  id: 'ad-privesc',            // stable slug; also the localStorage progress/notes key
  domain: 'ad',                // 'general' | 'ad' | 'web' | 'linux' | 'api' — drives the --dom-* chip color
  scopes: ['interno'],         // which SCOPES ids this step appears in — drives the wizard/stepper/progress
  phase: 'post-exploitation',  // must be one of the ids in PHASES
  title: '...', shortDescription: '...',   // shortDescription is the always-visible one-liner in the collapsed card
  methodology: { ptes: [...], wstg: [...], owaspTop10: [...], nist: [...], mitreAttack: [...], cwe: [...] }, // optional, all arrays optional
  oblivionTip: '...',          // optional, only used on recon-osint today — cross-reference to the sibling OblivionSec CLI
  content: {
    objetivo, quandoExecutar, comoValidar,   // plain strings
    oQueProcurar: [...], observacoes: [...],  // string arrays -> bullet lists
    comandos: [{ label, tool, command, note }],   // command may contain <<TARGET>>/<<PORT>>/<<USER>>/<<DOMAIN>>/<<LHOST>>/<<LPORT>> tokens
    ferramentas: [{ name, description, link }],
    exemplos: [{ title, description, code }],
    checklist: [{ id, text }]   // id must be prefixed with the step id (e.g. 'ad-privesc-01') and unique across the whole file
  }
}
```

### Adding a new step

1. Append an object to `STEPS` (before the `/* END STEPS */` sentinel) with a real `phase` (must match an id in `PHASES`), a `domain`, and a `scopes` array of one or more `SCOPES` ids (a step with no matching scope is unreachable — it never enters any wizard). There is no stub/placeholder state — only add a step once you're writing its real `content`. **Do not** add unfinished/empty steps "to fill out the nav" — the whole point of the rewrite was removing exactly that.
2. Checklist item ids: prefix with the step id (`<step-id>-01`, `-02`, ...) — they're the localStorage key alongside the step id, so they must be unique file-wide, not just within the step.
3. In any `comandos[].command` string, use `<<TARGET>>`, `<<PORT>>`, `<<USER>>`, `<<DOMAIN>>`, `<<LHOST>>`, or `<<LPORT>>` wherever a value should come from the user's session variables (see below) instead of hardcoding an example IP/domain/username. Leave illustrative secondary values (a *victim* username in a lateral-movement example, a placeholder hash) as plain text — the token set intentionally covers only the "current session" variables, not every string in every command.
4. **Always end every array item except the very last one with a trailing comma**, same discipline as v1 — the array ends with `/* END STEPS */` right before `];`, and forgetting the comma on what was previously the last item is the single most common way this file's script breaks silently. Run the syntax-check one-liner above after any hand edit.
5. If a step's example `code:` string ever needs to contain a literal `<script>...</script>` (e.g. an XSS/CSRF PoC), see the `</script>` gotcha below — do not paste it in raw.

## Variable substitution engine

`VAR_FIELDS` (near the top of the script) defines the six session fields rendered in the sticky session bar: `target`, `port`, `user`, `domain`, `lhost`, `lport`. Values are stored per-engagement at `state[engagementId].vars`, alongside `progress` and `notes`.

Command templates use `<<TOKEN>>` (double angle brackets), **not** `{{TOKEN}}` — `{{...}}` is reserved because SSTI example payloads in this content legitimately contain literal `{{7*7}}`-style text, and using the same delimiter for both would make one break the other. `commandToHTML(template, vars)` walks the template with a regex, HTML-escapes literal segments, and replaces a token either with the escaped current value or, if empty, a `<span class="var-empty">TARGET</span>` placeholder so the user can see at a glance which fields still need filling. `updateAllCommandOutputs()` re-runs this over every currently-rendered command block on every keystroke in the session bar (see the no-re-render note in Architecture above) — it's cheap because it only touches `innerHTML` of existing `<code>` nodes, not the surrounding page.

The "Copiar" button copies `codeEl.textContent` — i.e. whatever is currently substituted, including any literal `TARGET`-style placeholder text for fields the user hasn't filled in yet. That's intentional: it signals "you forgot to fill this in" rather than silently copying a broken command.

## Router

Hash-based. `parseHash()` recognizes `#/inicio` (home/hub, and the **empty hash defaults here** — v14), `#/escopo` (scope picker), `#/etapa/setup` (setup form), `#/etapa/<phaseId>` (a wizard phase), `#/etapa/<phaseId>/<stepId>` (same, but auto-selects that step's domain filter, force-expands its details panel, and scrolls to it — what search links to), `#/resumo` (progress summary), `#/achados` (and `#/achados/<findingId>` — opens the **Achados tab of the Pentest Automatizado screen** and scrolls to/focuses that finding, v14), `#/relatorio` (generated report), `#/pentest-automatizado` (Pi Agent hub — also `#/pentest` and the legacy `#/automacao`, all → `view:'automacao'` = Pipeline tab; see "Pi Agent" below), and `#/metodologias` (reference page). `#/fase/...` is kept as a legacy alias for `#/etapa/...`.

`parseHash()` only reads the URL; **`resolveRoute()` is where the guards live** and returns the real destination plus an optional canonical `redirect`: (1) `#/inicio` and `#/metodologias` pass through with **no** scope guard (the home page works with or without a scope); (2) otherwise no `engagement.scope` → `#/escopo`; (3) `#/achados`/`#/relatorio`/`#/automacao` pass through with only the scope guard — you can log a finding or configure/run the agent before the setup is complete, unlike every other route; (4) a phase requested with an incomplete setup → `#/etapa/setup` (the *only* block in the app for phase routes); an unknown/out-of-scope step id falls back to the first wizard step. `render()` honors `redirect` by setting `location.hash` and returning, letting the `hashchange` listener re-render. `navigate(hash)` sets `location.hash` (or calls `render()` directly if the hash is unchanged).

## Persistence — 4 localStorage keys, deliberately kept minimal

```
offsecManual.engagements         -> [{ id, name, scope, client, createdAt, updatedAt }]
offsecManual.currentEngagementId -> "<id>"
offsecManual.agent               -> { url, token }   // Pi Agent connection — GLOBAL, not per-engagement (v8) — see "Pi Agent" below
offsecManual.state               -> { [engagementId]: {
  progress:  { [stepId]: { [checklistItemId]: 'done' | 'na' } },   // absent key = pending; legacy `true` still reads as done
  evidence:  { [stepId]: { [checklistItemId]: "text" } },
  notes:     { [stepId]: "text" },
  vars:      { target, port, user, domain, lhost, lport },
  setup:     { [intakeKey]: "text" },
  findings:  [{ id, title, severity, cvss, cwe, affected, description, evidence, recommendation, status, stepId, phase, domain, createdAt, updatedAt, sourceTool?, items?, meta? }],
  scans:     [{ id, tool, target, stepId, phase, domain, status, createdAt, updatedAt, findingIds, summary }],
  agentQueue: [tool, tool, ...]  // remaining tools in the current "Rodar tudo" pipeline, consumed by agentQueueNext()
} }
```

`engagement.scope` is a `SCOPES` id or `null`. It replaced the old `engagement.type` (whose values — `pentest-externo`, etc. — never matched any scope id); `ensureEngagements()` migrates any legacy `type` to `scope` via `LEGACY_TYPE_TO_SCOPE`, nulls out unknown scopes, and deletes the stale `type` key. The `_scratch` ("Rascunho") default engagement starts with `scope: null` so first load lands on the scope picker; it can never be deleted (`deleteEngagement` no-ops for it).

**The Pi Agent connection (`url`+`token`) is GLOBAL (v8), living in its own `offsecManual.agent` key — not inside `state[engId]`.** It was per-engagement through v7, which meant every new engagement started with an empty connection and the Automação page nagged "Configure o agente Pi" again, even though the Pi is the same physical box for every engagement. `getAgentConfig()`/`setAgentField()` now read/write `LS_AGENT` directly; `ensureAgentConfig()` (called once in `init()`) migrates any legacy per-engagement `state[engId].agent` up to the global key on first load (also covers importing an old backup). `scans` and `agentQueue` stay **per-engagement** on purpose — a scan's findings must attach to the engagement that launched it. Consequence: the connection is now the same across all engagements, and switching engagements no longer changes which Pi you talk to. If you touch any agent code, read the connection via `getAgentConfig()`, never `state[engId].agent` (that field no longer exists).

`setup` holds the scope's free-text `intake` answers; `evidence` and `findings` were added in v4; `scans` and `agentQueue` were added in v7 for the Pi Agent (see below). Those live inside `state`, so **export/import covers them**. The agent **connection** is deliberately **not** exported (it's in `LS_AGENT`, and `exportData()` only serializes `engagements`+`state`+`currentEngagementId`) — a v8 change with a security upside: the Pi token no longer rides along in plaintext in the backup JSON (this reverses the earlier "token in export is fine" call; don't re-add it to the export without checking with the user). `getEngagementState()` guarantees `vars`/`setup`/`evidence` as `{}` and `findings`/`scans`/`agentQueue` as `[]`. Checklist toggles save and re-render immediately; notes, session `vars`, `setup`, and per-item evidence persist on every change but deliberately **do not** trigger `render()` (see Architecture) — evidence textareas are debounced the same way notes are. If you add a new persisted field inside an engagement, it rides along in export/import automatically as long as it lives under `state`.

Progress is always scope-scoped: `countProgress(engId, steps)` is the shared counter, and `phaseProgress`/`overallProgress`/`engagementProgressPct` all feed it `stepsForScope(...)`/`allStepsForScope(...)` — never the whole `STEPS` array — so a Pentest Interno can actually reach 100% without web/api steps dragging the denominator. `countProgress` delegates the per-step math to `checklistTally(engId, step)`, which is where the tri-state rule actually lives: `'na'` items are removed from **both** numerator and denominator (they don't count as done, but they don't drag the percentage down either), so `stepProgress`/`phaseProgress`/`overallProgress` all inherit that behavior automatically — do not reintroduce a raw `p[it.id]` truthiness check anywhere, it would silently count `'na'` as done again.

**Findings.** `severity` is one of the five `SEVERITIES` ids (`critico`/`alto`/`medio`/`baixo`/`info`, each with a label and a `--sev`-driving color via `severityMeta()`); `status` is one of `FINDING_STATUS` (`rascunho`/`aberto`/`confirmado`/`reportado` — `rascunho` first, added in v7 for Pi Agent auto-created findings pending human review, see "Pi Agent" below). `addFinding(partial)` seeds `affected` from the current session `target` and tags `stepId`/`phase`/`domain` when called from a module's "+ Registrar achado deste módulo" button (`[data-add-finding]`, wired to `stepActionHTML`'s per-card button) — findings created from `#/achados`'s own "+ Novo achado" are untagged (and default to `status: 'aberto'`, not `rascunho` — only the Pi Agent path passes `rascunho` explicitly). Text/textarea fields in the finding editor save via the generic `data-finding`/`data-field` `input` listener (no re-render, same reasoning as notes); the severity/status `<select>` elements go through a separate `change` listener that **does** call `renderAchados()`, because the severity chip's color needs to update immediately and a `<select>` has no mid-keystroke focus to lose.

No external dependency was added. The pieces:
- **Dashboard** (`achadosDashHTML`): a proportional severity **distribution bar** (`.ach-dist`/`.ach-dist-seg`, `flex-grow` = per-severity count) plus **clickable filter chips** (`.ach-chip`). These replaced v11's reuse of the shared `.severity-tally`; the report's `severitySummaryHTML` still uses `.severity-tally` untouched. `achadosSevFilter` (in-memory) narrows to one severity; re-clicking the active chip or the "Limpar filtro" toolbar button clears it.
- **Items collapsed by default** (`achadosRowHTML` → `.ach-item`): `expanded = expandedFindings[f.id] === true` (v12 changed this from v11's auto-open-for-drafts). The collapsed head shows a severity chip, title, the **affected asset preview** (`.ach-item-affected`) and status/CWE/tool/tag/draft/stalled badges — enough to triage without opening. Grouped under `.ach-group` severity bands (`achadosGroupedRowsHTML`, crítico→info). The detail is only rendered into the DOM when expanded (lighter than v11's always-rendered-then-hidden), so toggling re-renders via `renderAchados()`.
- **Expand → formatted read view** (`achadosReadHTML`): a `.ach-spec` metadata grid (severidade/status/CVSS/CWE/ativo/detectado-por) + `.ach-prose` blocks for description/recommendation, with an **"Editar" button** (`data-finding-edit`, toggles the new in-memory `editingFindings` map) that swaps in `achadosEditHTML` — the same editable fields as always (`.achados-field`, `data-finding`/`data-field`, no field removed), so the existing input/change save handlers were untouched. Read mode is the default on expand; edit mode is default only for a brand-new finding (the `data-finding-new`/`data-add-finding` handlers set `editingFindings[id]=true`+`expandedFindings[id]=true` before navigating, which is why creating a finding still lands you in an open editor with the title focused).
- **Structured evidence rendering, v12 text heuristic + v17 real tables.** `achadosEvidenceHTML(f)` is the entry point now: if `f.items` (structured, from the Pi Agent — see the "Normalized result shape"/`meta` note in "Pi Agent" below) is present, it renders `paItemsTableHTML(f.items, f.sourceTool)` — a genuine `<table>` with per-tool named columns (`RESULT_COLUMNS`: nmap gets Proto/Serviço/Produto/Versão, httpx gets Status/Título/Tecnologias/Servidor, etc.), status-code cells still getting the same color-coded pill (`.is-2xx` green / `.is-3xx` amber / `.is-4xx`/`.is-5xx` red). Otherwise it falls back to `formatEvidenceHTML(f.evidence)`, the original v12 heuristic: multi-line **token-like** text (3+ lines, no blank line, every line a whitespace-free token after stripping a trailing status code) becomes the old index+status-badge list; anything else (request/response, prose) becomes a monospace `<pre class="ach-pre">`. The fallback is what manually-created findings and any finding without `items` still get — nothing regressed, v17 only added a better *first* option. Individual (non-aggregated) vuln findings that carry a singular `f.meta` instead of `f.items` get its keys folded into the `.ach-spec` grid (via `META_LABELS`) as extra rows — e.g. sqlmap shows Parâmetro/Tipo/Payload, nuclei shows Template/Matcher/Tags — alongside severity/status/CVSS/CWE, so a vuln finding's key detail is visible without parsing the evidence blob.

`#/relatorio` (`renderRelatorio`) and `buildReportMarkdown()` are two independent renderers of the **same** sorted-by-severity findings list — one to `innerHTML` (styled, for on-screen review and printing), one to a markdown string (for `downloadReportMarkdown()`). Neither was touched by the v12 achados rebuild or v17's structured tables — both still read `f.evidence` (the flattened text), never `f.items`/`f.meta`. If you add a field to the finding model, update both report renderers, or the two outputs will drift.

**Draft findings never reach the report.** Both `renderRelatorio()` and `buildReportMarkdown()` start from `nonDraftFindings()` (`getFindings().filter(f => f.status !== 'rascunho')`), not the raw `getFindings()` list — `#/achados` is the only page that shows `rascunho` items, tagged with `.finding-draft-tag`. `severityCounts()`/`severitySummaryHTML()` both take an optional `list` param precisely so the report's executive summary can be recomputed off the filtered set instead of double-counting drafts that don't appear below it. If you touch either report renderer, keep this filter — it's the whole point of `rascunho` existing (see "Pi Agent" below): automated scanner output must never silently reach the polished deliverable unreviewed.

The report page's print target is deliberately narrow: `.no-print` (plus explicit selectors for `.phase-toolbar`, `.achados-toolbar`, `.ach-dash`, `.step-add-finding`, `.ach-item-del`, `.ach-detail-actions`, `.checklist-evi-toggle`) hides every action control in `@media print`, and `.step-detail[hidden]`/`.checklist-evidence[hidden]` are forced visible so a printed checklist page shows its context/evidence even if a toggle was collapsed on screen. The two supported print targets are a phase's checklist (Ctrl+P from any `#/etapa/<phase>`) and `#/relatorio` itself — on `#/achados` (v12) only the currently-**expanded** findings print their detail, since collapsed items no longer render a hidden detail into the DOM at all (the detail is built only when expanded); that's an acceptable "print what you opened" behavior, and the real deliverable is `#/relatorio` anyway.

## Pi Agent (v7)

`pi-agent/` is a **separate, standalone Python stdlib HTTP service** — not part of the `index.html` single-file app, and not loaded by it in any build/bundling sense. It exists purely so a companion machine (a Raspberry Pi or any box with the right tools on `PATH`) can execute real recon/vuln scans on request and hand back structured results over `fetch()`. This is the **one deliberate exception** to this repo's "no backend" rule — see the top-of-file note and `pi-agent/README.md` for the full rationale and setup/security details. `index.html` still works standalone with zero setup; the automation page simply has nothing to trigger until an agent is configured.

**Three tool families feed the pipeline:** the usual recon/vuln binaries (`nmap`, `subfinder`, `httpx`, `nuclei`), five subcommands of [OblivionSec](https://github.com/AndreNunes7/OblivionSec) — the user's own sibling CLI project (already cross-referenced from `recon-osint`'s `oblivionTip` before the agent existed) — via its `oblivion` console script (`pip install -e .` in that repo), and (v8) two active-exploitation tools, `sqlmap` and `dalfox`. `oblivion webrecon` is the directory/file brute-force tool (dirsearch/gobuster-style); `oblivion subdomains`/`passive`/`webvuln`/`exposed` cover multi-source subdomain enum, a passive headers+fingerprint combo, quick web-vuln checks (CORS/redirect/methods/cookies), and known-sensitive-path exposure, respectively. All five share one calling convention — `oblivion <subcmd> -u|-d <target> -o <raw_path> --format json -q` — because `oblivion`'s own `per_target()`/`_save()` dispatch (in its `cli.py`) treats an explicit `-o <path>` as "write JSON exactly there," the same deterministic-output-path contract every other tool in `tools.py` already relies on (nmap's `-oX`, subfinder's `-o`, etc.) — no timestamp-guessing needed. `oblivion webvuln`'s findings already use `critical/high/medium/low/info` severities (same scale as nuclei), so `parsers.py` reuses `NUCLEI_SEVERITY_MAP` for it (aliased `OBLIVION_SEVERITY_MAP`) rather than duplicating the table. `sqlmap` is the one tool whose output isn't a single deterministic file — it writes a `log` under `--output-dir/<host>/`, so `build_sqlmap_argv` points `--output-dir` at the job's own directory (`os.path.dirname(raw_path)`, already unique per job) and `parse_sqlmap_log` globs `<job_dir>/*/log` instead of reading `raw_path` directly; the tradeoff is that `GET /jobs/{id}/raw` 404s for sqlmap jobs (no `raw.*` file ever gets written) — accepted since the UI only ever calls `/result`, never `/raw`. `dalfox`'s JSON field names aren't pinned to one schema in `parse_dalfox_json` (defensive `.get()` with fallbacks) since they've shifted across releases — verify against your installed version if a run's findings look empty.

**All automation lives on its own screen, "Pentest Automatizado" (`#/pentest-automatizado`, legacy alias `#/automacao`) — not embedded in module cards.** An earlier iteration put an "Executar via Pi" panel directly inside the `scan-network`/`scan-web-surface` step cards; user feedback was that this didn't match the intended workflow ("insiro meu alvo, ele manda pra Pi, ela roda tudo, me traz os achados") and scattered a single concern across unrelated cards. `stepActionHTML()` no longer renders anything agent-related — it's back to just "Passo a passo" + Ferramentas, per the original Disclosure pattern. All agent UI is the **Pipeline tab** of `renderPentestAutomatizado()` (v14, renamed from `renderAutomacao`; see "Achados & Relatório" above), reached like any other engagement-scoped page (sidebar link "Pentest Automatizado", same `resolveRoute()` treatment as `#/achados`/`#/relatorio`: needs a scope, not a completed setup).

**Backend shape** (`pi-agent/agent.py` + `jobs.py` + `tools.py` + `parsers.py`): a `ThreadingHTTPServer` with a hand-rolled router, no framework dependency (Python 3 stdlib only — nothing to `pip install` on a headless Pi). Every route requires `Authorization: Bearer <token>` (including `/health`, so an unauthenticated request can't even learn which tools are installed). `tools.py`'s `TOOL_REGISTRY` is the single allowlist for what a client can trigger: target must match a conservative hostname/IP/CIDR regex, tool parameters are restricted to a small fixed enum per tool (nmap's scan profile, nuclei's severity list) — **never** a free-text flags string — and the resulting argv is passed to `subprocess.Popen(argv, shell=False)`, so there is no shell to inject into even if validation had a gap. A job runs in a background thread, is killed if it exceeds `job_timeout_seconds` (default 1800s/30min), and its raw output + parsed result live as files under `pi-agent/jobs/<id>/` on the agent machine — the browser never receives more than a normalized result array and a job status/summary, never the raw files, keeping `state[engId].scans[]` a lightweight receipt rather than a dump of scan output.

**Normalized result shape**, what every parser in `parsers.py` converges on: `{ title, severity, affected, description, evidence, sourceTool, meta }`, `severity` always pre-mapped into this app's own `SEVERITIES` ids (nuclei's `critical/high/medium/low/info` maps directly; nmap open ports/httpx probes/subfinder hosts all come through as `info` since they're recon, not judged vulnerabilities). **The browser no longer turns these 1:1 into `addFinding()` — `agentHandleJobDone` enriches and filters them first (v8):** (1) it fills `cwe` from the tool's `AGENT_TOOL_DEFS.methodology.cwe` and `recommendation` from a new per-tool `AGENT_TOOL_DEFS.recommendation` string (the vuln tools — sqlmap/dalfox/oblivion-webvuln/oblivion-exposed — carry one; recon tools don't, since their findings are `info`), so automated findings arrive with CWE and a starter remediation instead of blank fields; (2) it **deduplicates** via `findingKeyExists(title, affected, sourceTool)` — re-running the pipeline against the same target skips findings that already exist rather than duplicating the list; (3) it **aggregates recon noise** — tools carrying an `AGENT_TOOL_DEFS.aggregateNoun` (nmap/subfinder/httpx/oblivion-subdomains/oblivion-webrecon) collapse a whole job's N near-identical `info` results into **one** finding (`"N <aggregateNoun> em <target>"`, `info`, full list in `evidence`) instead of one-per-port/subdomain/path. The vuln tools (nuclei/sqlmap/dalfox/oblivion-webvuln/oblivion-exposed) deliberately do **not** aggregate — each is an individual finding that matters. `scan.summary` now carries `{ count, skipped }` and the toast reports "N novo(s), M já existia(m)". All still land as `status: 'rascunho'`.

**`meta` — structured per-result fields (v17), additive and optional.** Every parser in `parsers.py` may attach a flat `meta` dict alongside the free-text `evidence` string — e.g. nmap's `{host, port, protocol, service, product, version}`, httpx's `{statusCode, title, tech, webServer, contentLength}`, nuclei's `{templateId, matcherName, tags}`, sqlmap's `{parameter, type, payload}`. This exists so the browser can render a real table/spec instead of `formatEvidenceHTML`'s old regex-based line-guessing (see "Achados & Relatório" below). `agentHandleJobDone` routes it two ways depending on `AGENT_TOOL_DEFS.aggregateNoun`: (1) **aggregated recon tools** — `items` on the collapsed finding is `rawResults.map(r => Object.assign({label: r.affected || r.title}, r.meta || {}))`, one row per port/host/path; (2) **individual vuln tools** — `meta` (singular) is passed straight through per finding. `evidence` (the flattened text list, or the raw payload/curl-command/JSON string) is always still populated too — it's what `buildReportMarkdown`/`renderRelatorio` consume, untouched by this change. A parser that omits `meta` (or a manually-created finding, which never has `items`/`meta`) just gets the pre-v17 text-heuristic rendering — nothing breaks.

**Findings show their origin (v8).** `sourceTool` used to be write-only; now `findingFormHTML` renders a `via <tool>` chip (`.finding-tool-tag`) on the card, and both report renderers (`renderRelatorio` + `buildReportMarkdown`) emit a "Detectado por: <tool> (automação Agente Pi)" row — keep the two report renderers in sync as always.

**`AGENT_TOOL_DEFS`** (array, not a per-step map) is the single source of truth for every automatable tool: `{ tool, label, desc, stepId, phase, domain, paramKey, paramLabel, defaultParam, paramOptions, methodology }`. Its **array order is the "Rodar tudo" execution order**, and is deliberately written in `PHASES` sequence — info-gathering (`oblivion-passive`) → recon (`oblivion-subdomains`, `subfinder`) → scanning (`nmap`, `httpx`, `oblivion-webrecon`) → vuln-analysis (`nuclei`, `oblivion-webvuln`, `oblivion-exposed`) → exploitation (`sqlmap`, `dalfox`, added v8) — **18 tools in `AGENT_TOOL_DEFS` after v28**. v24/v25 added testssl/wpscan/gitleaks/ffuf/nikto/osv-scanner and v26 added wafw00f/arjun/katana (peaking at 20), but **v27 removed 5 tools from `AGENT_TOOL_DEFS`** at the user's request — gitleaks/osv-scanner (repo-only, never worked against a web target) and testssl/nikto/wpscan (not installed on their Pi) — so the pipeline UI only lists tools that actually run. **v28 re-added nikto** (installed on the Pi — see its note below), bringing the pipeline to 18. The still-absent 4 (gitleaks/osv-scanner/testssl/wpscan) stay in `pi-agent/tools.py`'s `TOOL_REGISTRY` (latent backend capability; re-add a one-line `AGENT_TOOL_DEFS` entry to restore any). v27 also **added two Information Gathering tools next to `oblivion-passive`**: `gau` and `waybackurls` (passive historical-URL discovery from public archives — Wayback/CommonCrawl/OTX/URLScan for gau, +VirusTotal for waybackurls), both installed on the Pi (Go binaries). This directly answered the user's "besides oblivion passive, use other information-gathering tools" ask and their "always start the pipeline at Information Gathering" ask (see the restart-clean note below). Not just source-code order (the info-gathering/recon ordering flipped in v13 to match the `PHASES` reorder; keep the array in `PHASES` sequence if you touch either). v26 also deepened the two exploitation tools within their existing single-`paramKey` picker rather than adding a second param field (the pipeline UI only renders one dropdown per tool): `sqlmap`'s `profile` gained `safe-dbs`/`level2-dbs`/`aggressive-dbs` variants that add `--dbs` (enumerates databases only *after* sqlmap has already confirmed the injection, so no added risk beyond the level/risk already chosen — `parse_sqlmap_log` reads the resulting "available databases" block as an extra `info` finding), and `dalfox` gained its first-ever `paramKey` (`deep`: normal/deep, the deep option adding `--deep-domxss` for more thorough but slower DOM XSS coverage). A tool can carry `targetKind: 'repo'` (gitleaks, osv-scanner — they `git clone` the target instead of probing it as a web/host target) — `agentRunnableToolDefs()` excludes these from "Rodar tudo" since the session's web target always fails their clone step; they still render in the pipeline UI with a "requer repo git" chip instead of vanishing. The frontend also caches `GET /api/v1/health`'s per-tool install map (`agentHealthCache`/`toolInstalled()`, refreshed on load, on agent config save, and opportunistically when the Pipeline tab renders) so a tool missing from the agent's `PATH` shows a "não instalado" chip and is skipped by the batch queue instead of silently 400ing (v26). `stepId`/`domain` only tag findings (`addFinding`'s `partial`) for continuity with the rest of the app's tagging; `phase` additionally drives which stage section a tool's node renders under (see below). `methodology` (v8) is shaped exactly like a `STEPS` entry's `methodology` field (`ptes`/`wstg`/`owaspTop10`/`mitreAttack`/`cwe`) and is rendered in the legend via the same `methodologyRowHTML()` every module card already uses — added because the user pushed back on the automation stages looking like an arbitrary bucket list instead of a named methodology; reuse this field (don't invent a parallel tagging scheme) if you add a 12th tool. Two more per-tool fields drive the v8 finding enrichment above: `recommendation` (starter remediation text, on vuln tools only) and `aggregateNoun` (on recon tools only, e.g. nmap's `'portas/serviços abertos'`) — a 12th tool should carry whichever fits its nature. Connection settings are **global** (`offsecManual.agent`, read via `getAgentConfig()`), configured once in the engagement modal (`data-agent` inputs, same debounced-save-no-render pattern as `data-var`/`data-setup`) and shared across all engagements — see the Persistence section's Pi-Agent-connection note.

**Target input lives on the Automação page (v8).** `automacaoConsoleHTML` renders the session `target` as an editable `<input data-var="target" id="automacao-target-input">` (replacing the old static "Alvo ativo" span). The existing `#content` `data-var` input handler already saves via `setVar` and mirrors into `#vars-bar`, so no new handler — the whole automation flow (set target → run) now fits on one screen without opening the session bar first. When there are draft findings, the console also shows a `.automacao-review-cta` ("Revisar N achado(s) em rascunho →") below the run button, a clear post-run path to `#/achados`.

**Visual treatment: a "mission console" card with a stage grid.** This page went through many visual cuts, each checked against the user rather than guessed blind: a flat list of buttons (ugly) → one long horizontal strip mixing every tool into a single row (hid the PTES stage structure) → three side-by-side mockups (sober list / terminal-CRT / vertical rail) from which the user picked the vertical rail → live, the user actually preferred the horizontal-node look and asked only to fix "monocromático" and "apertado" on it → restoring the horizontal per-stage row with a fixed-width `.pipeline-connector` (`width: 44px` instead of `flex: 1`, which had stretched into a long dead-looking hairline) fixed the connector but exposed the real issue on a real desktop screen: nodes defaulted to `flex: 0 1 auto` (hug their own content), so a short 2–3-node stage row left a large empty rectangle down the right side of the wide `.automacao-console` panel — caught twice from screenshots ("esse espaço em branco gigante", then again after a flex-grow attempt still left a smaller version of the same hole). **The fix that actually holds is architectural, not a flex tweak**: `stagesHTML()` wraps every stage in `.automacao-stages-grid` (`display: grid; grid-template-columns: repeat(auto-fit, minmax(230px, 1fr))`), so each `.automacao-stage` is a self-contained bordered card sized to its own content, and a wide viewport fits *multiple stage cards side by side* instead of stretching one sparse row to fill the whole panel — the leftover space at the end of the last grid row is ordinary trailing whitespace after a card (normal, expected), not a bounded empty box butted up against real content (broken-looking). Inside each stage card, tools stack vertically as compact `.pipeline-node` rows (small dot + name + right-aligned status, `display:flex; align-items:center`) rather than a horizontal chain — there's no connector at all anymore, which also permanently removes the whole class of "connector stretches into dead space" bug. `.pipeline-node-dot` at rest (`is-idle`) takes its color from the tool's own `domain` via a `data-domain` attribute (`--dom-web`/`--dom-general`) instead of flat gray, so a stage with unstarted tools isn't monochromatic. Each tool's state — `idle`/`queued`/`running`/`done`/`error` — comes from `agentNodeState(def)`: an active scan wins, then queue membership, then `lastScanFor()`'s result, so it reflects the *current* batch instantly even if a stale result from days ago would otherwise say "done." The running dot pulses via `brand-blink` (opacity only) — never a glow, per this file's "hairline lift" depth philosophy. Below the grid: an overall progress bar (`automacaoProgressHTML()`, `doneCount/total` across *all* tools) and the run control (`.automacao-run-btn`, an inline pill, not full-width) — the "running" state swaps it for a plain inline-text `.is-running` label with live `doneCount/total`. Below the console card, `.automacao-tool-legend` keeps each tool's one-line description visible, and `.agent-log` renders execution history as color-left-bordered monospace rows — a terminal-log look, leaning into the "hacker" aesthetic the user actually asked for.

**Gotcha: this page's empty-space bugs only ever showed up on a real desktop-width screen (1200px+), never on the mobile widths that got tested first each round.** Three consecutive rounds of "still looks wrong" were the same root cause wearing different clothes — a variable-length row (2–3 tools) inside a fixed-wide, non-scrolling container will always leave dead space *somewhere* unless the layout mechanism itself is width-aware (grid `auto-fit`), not just flex-grow tuned by hand. If you touch `.automacao-stages-grid`/`.automacao-stage`/`.pipeline-node` again: verify at 1200px+ before calling it done, and reach for `grid-template-columns: repeat(auto-fit, minmax(...))` before reaching for another round of `flex`/`min-width`/`max-width` tuning — the grid approach is what actually stopped the bug from recurring, three flex-based fixes in a row didn't.

**v8 — stage index + PTES ref chip, per-tool methodology tags, flatter card styling.** The user's complaint was that the stage headers ("Recon", "Information Gathering", "Scanning", "Vulnerability Analysis") read as an arbitrary bucket list rather than a named methodology, even though they were already literally `PHASES[].label` in PTES order. The fix wasn't renaming anything — `PHASES` is the app-wide phase taxonomy, shared with the wizard/stepper, and staying consistent with it matters more than this one page — it was making the existing framework tie *visible*. `stageSectionHTML(phaseObj, index)` now takes an index computed over only the phases that actually have automatable tools (not raw `PHASES.indexOf`, same "don't count empty sections" instinct as `wizardSteps`) and renders it as `.automacao-stage-index` (`01`/`02`/...) plus `.automacao-stage-ref` showing `phaseObj.ref` (e.g. `PTES §2`) as a small pill — the same index+reference pairing the wizard stepper already uses elsewhere in the app. Each `AGENT_TOOL_DEFS` entry also grew a `methodology` field (see above) rendered per-tool in the legend via the existing `methodologyRowHTML()`, so `sqlmap`/`dalfox` show `CWE-89`/`CWE-79`/`T1190`/`A03:2021-Injection` tags and every other tool shows its own MITRE ATT&CK reconnaissance/scanning technique — reusing the exact tag component every module card in the wizard already uses for the same purpose, not a bespoke one for this page. `.automacao-stage` moved from `--inset` background to `--panel` with a `border-left: 3px solid var(--signal)` (was a flat `--inset` box with no accent), and the console got a `::before` top hairline gradient in `--signal` — small additions on top of the existing "Console" token system (§ Visual design system below), not a new palette. `automacaoActionHTML()` renders a single "Rodar tudo via Pi" button; clicking it calls `agentRunAll()` directly, which seeds `state[engId].agentQueue` with every tool *after* the first and starts the first via `agentStartScan()` with that tool's `defaultParam` (there is no param picker in this flow — batch mode always uses defaults). Earlier versions gated this behind an inline "Confirmo autorização..." checkbox (`agentConfirmOpen['__run_all__']`, same in-memory-map pattern as `expandedSteps`); it was removed at the user's request after checking `agentStartScan()`'s fetch body — the frontend already hardcodes `confirm: true` on every job POST regardless of any checkbox state, and the real gate is server-side (`agent.py`'s `do_POST` rejects anything where `confirm is not True`, independent of what the browser sends). The checkbox was therefore pure click-friction with no authorization actually riding on it, so removing it didn't weaken anything — the target/tool list is still shown as a static caption (`.automacao-run-caption`) next to the button so you can see what's about to run before clicking. If you add a 12th tool, just insert it into `AGENT_TOOL_DEFS` at the right position for its phase — everything else (stage grouping, queue order, progress denominator, stage index numbering) picks it up automatically.

**The queue survives success *and* failure of each stage.** Every place a scan resolves — `agentHandleJobDone()` (done), the `error` branch in `agentPollTick()`, and both failure paths inside `agentStartScan()` itself (couldn't even start, or the fetch errored) — calls `agentQueueNext(engId)`, which shifts the next tool off `state[engId].agentQueue` and starts it. A single failed stage (e.g. a tool not installed on the agent) does **not** stop the pipeline; it's reported via toast and the batch moves on, which is what makes "insert target once, walk away, come back to achados" actually reliable. `currentScanFor(tool)` / checking membership in `agentQueueNext`'s queue is how `agentToolRowHTML()` shows "executando..." vs "na fila do pipeline" per tool without any separate confirm state.

**Builder signature contract (v28 — bug that silently broke the recon phase).** `jobs.py`'s `start_job` calls every tool's `build_argv` uniformly as `build_argv(target, params, raw_path, session)` — **4 positional args**. Any builder defined with only 3 (`def build_x_argv(target, params, raw_path):`) raises `TypeError` at job start, which crashes the request thread and returns an empty HTTP reply — the browser's `agentStartScan` catch fires and `agentQueueNext` skips to the next tool. This is exactly what made "Rodar tudo" appear to *start at gau* instead of `oblivion-passive`: the seven 3-arg builders (nmap, subfinder, and all five `oblivion-*`) each crashed and got skipped, so the first tool that actually ran was the first 4-arg builder (gau). Fix: **every** builder now takes `session=None` even if it ignores it. `test_all_registered_tools_well_formed` now calls each `build_argv` with the full 4-arg signature (and `pre_build` with 3) so a mismatch fails the suite instead of silently dropping a tool at runtime. If you add a tool, its builder MUST accept `session=None`.

**nikto (v28, re-added).** After being removed in v27 (not installed), nikto was installed via `sudo apt install nikto` on the Pi (pulls its Perl deps: XML::Writer, libwhisker2, Net::SSLeay). The apt package is **2.1.5**, which does **not** support `-Format json` ("Invalid output format") and whose **CSV writer is buggy** (injects `SCALAR(0x..)`/`HASH(0x..)` refs mid-field). So `build_nikto_argv` uses `-Format xml` and `parse_nikto_xml` walks the well-formed `<item>` elements (description/uri/method/osvdbid). It also passes `-Tuning 123bde` to bound the scan to high-signal check groups — a full untuned nikto runs 6000+ checks and would block the pipeline 15-30 min. Back in `AGENT_TOOL_DEFS` under scanning.

**Stopping the pipeline + clean restart (v27).** A **"Parar pipeline"** button (`.automacao-stop-btn`, `data-agent-stop`) renders next to the running indicator whenever a batch is active. `agentStopAll()` empties `state[engId].agentQueue`, bumps `agentQueueGen` (so any pending `agentQueueNext` start aborts on the gen check), marks each queued/running scan `status:'error'`+`cancelled:true` locally (the `cancelled` flag makes `pipelineToolRowHTML` show a "cancelado" chip instead of "falhou"), and fires `POST /api/v1/jobs/{id}/cancel` per in-flight scan. Server side (`pi-agent/jobs.py`), `JobManager` now tracks the live `Popen` per job (`_running`, guarded by `_proc_lock`) and a `_cancelled` set; `cancel_job()` kills the process tree (`_kill_tree`, the same killpg path used for timeouts) and the worker, seeing the job in `_cancelled` after `proc.wait()` returns, marks it `error`/`'cancelado pelo usuário'` and **skips the parse** so partial output never becomes a finding (a job still `queued` in the concurrency semaphore is marked cancelled directly). Separately, `agentRunAll()` now **discards prior completed/failed scan receipts** (`st.scans = st.scans.filter(status==='queued'||'running')`) at the start of every run, so the pipeline visibly restarts from the top (Information Gathering) instead of showing later-phase tools still "concluído" from an earlier run — this was the user's "always start at information gathering" complaint (the batch always *did* start at `AGENT_TOOL_DEFS[0]` = `oblivion-passive`; the stale green nodes just made it look otherwise). Findings persist (they live in `state[engId].findings`, not `scans`).

**Tools that read stdin / write stdout (v27).** Two `TOOL_REGISTRY` flags generalize the runner for tools that don't fit the "`-o <file>`" contract: `stdin_target` feeds `target+'\n'` to the process stdin (waybackurls only accepts a domain on stdin), and `output_stdout` points the process stdout **at `raw_path`** instead of `stdout.log` (waybackurls writes URLs to stdout, no output flag). `_run_worker` reads both from `spec`. `gau` needs neither (positional domain arg + `--o` file). Both are domain-oriented, so the frontend resolves their target to a bare host via `agentHostFromTarget()` (strips scheme/port/path off a URL) in `agentToolTarget()` — the `AGENT_DOMAIN_TOOLS` set (subfinder/gau/waybackurls) picks `vars.domain` first, else the derived host.

**Polling never calls `render()`.** A single `setInterval(agentPollTick, 5000)` started once in `init()` walks `state[engId].scans` for anything `queued`/`running` and, on a status change, mutates state and calls `refreshAutomacaoIfActive()` — a small helper that re-renders whichever of the two pages (`renderAutomacao()`/`renderAchados()`, see "Achados & Relatório" above) matches `resolveRoute().view`, so a background pipeline stage completing while the user sits on `#/achados` editing a finding refreshes that finding list in place instead of yanking them over to `#/automacao`. The one DOM node updated unconditionally, outside that check, is `#agent-job-badge` — a static node living as a sibling of `#vars-bar` inside `.session-bar` (**not** inside `#content`, so it survives every `render()` call untouched); `updateAgentBadge()` only ever sets its `textContent`/`hidden`/class, mirroring the "don't rebuild the DOM under a focused control" discipline documented for `data-var` inputs in Architecture above — clicking the badge navigates to `#/automacao`. Polling is scoped to whatever engagement is currently active (`getCurrentEngagementId()`) — switching engagements pauses polling for the one you switched away from (the job keeps running on the agent regardless; the app just stops checking on it until you switch back), a deliberate simplification to avoid ever attaching a finding to the wrong engagement.

## Productivity tools on the phase page (v4)

`renderPhasePage()` renders a `.phase-toolbar` above the step list (only when the domain-filtered list is non-empty): **"Copiar todos os comandos"** (`[data-copy-all]`) joins the `textContent` of every currently-rendered `code[data-cmd-tpl]` with `\n` and reuses `copyText()` — it copies whatever is currently substituted, same "TARGET placeholder signals an unfilled field" behavior as the per-command Copiar button. **"Ocultar/Mostrar concluídos"** (`[data-hide-completed]`) toggles the in-memory `hideCompleted` flag and filters out any step whose `stepProgress().pct === 100`; the toggle button itself always stays visible (with a live count) even when everything is hidden, and the empty-state message changes to explain why the list looks empty rather than reusing the domain-filter empty-state text.

## Clipboard copy

`copyText()` tries `navigator.clipboard.writeText` first and falls back to a hidden `<textarea>` + `document.execCommand('copy')` for contexts where the async Clipboard API is unavailable. Keep both paths if you touch this function.

## Visual design system

**v6 "Console" direction (current look).** The user compared three prototype directions and picked "Console" — a near-black terminal cockpit, command-first. What changed vs. earlier versions: (1) the palette accent `--signal` is now **phosphor teal** (`#37cdbd`) instead of brass/amber, on a darker near-black ground (`--ink: #07080b`); `--go` is lime, `--stop` rose. Only token *values* moved — every component that referenced `--signal`/`--go`/`--stop` re-skinned automatically. (2) Each module card is **two columns** (`stepRowHTML` → `.step-cols`): `.step-main` holds the command-hero "Passo a passo" + Ferramentas + footer, and a sticky `.step-rail` on the right holds a compact checklist with a mini count + progress bar; below 860px the rail stacks first (`order:-1`). (3) Substituted variables are wrapped in `.var-fill` (teal highlight) by `commandToHTML`, so the live value pops inside the command; empty tokens still get `.var-empty`. (4) The sidebar is a flat command-palette list (the stepper connector line was dropped), and `renderStepper` renders the active phase's **modules as indented sub-links** (`.phase-nav-sub`, deep-linking `#/etapa/<phase>/<step>` with a live checklist count). (5) `.content-inner`/`.session-row` share a `--content-max` width token (940px originally; **widened to 1200px in v13** at the user's request so commands/tables/result blocks have more room — prose stays readable via its own `max-width`, e.g. `.phase-desc`'s `74ch`; the stretch is only visible on viewports wider than the old cap). If the user wants to try a different direction later, the three prototypes were built as a standalone comparison artifact — the token remap is the cheap lever to re-skin.

Tokens live in `:root` at the top of `<style>`. `--signal` (phosphor teal) is the *only* interactive accent and is used sparingly; `--go`/`--stop` are semantic (checklist done / destructive actions) and are intentionally different hues from `--signal` so "this is clickable" and "this succeeded/this is dangerous" never look the same. `--dom-*` (ad/web/linux/general/api) are categorical identity colors for the domain dots/chips, unrelated to the semantic or accent colors. Monospace (`--font-mono`) is used as a structural UI element throughout — phase index numbers, var-bar labels, chips, methodology tags — not just inside command blocks; this is a deliberate nod to the audience (people who live in terminals), not an inconsistency.

**No emoji or pictographic icons anywhere in the UI** (stepper, buttons, headers) — this was an explicit user correction during v2 development. Sequence position is communicated with plain monospace index numbers (`01`–`0N`, N varying by scope) since the wizard is a genuine ordered sequence; do not reintroduce emoji as section markers if you add new UI. The `←`/`→` in the wizard nav and the `▸` details caret are plain text glyphs, not icon fonts.

The toggle+`.step-detail` are only emitted when `stepContextHTML` is non-empty. ## Known gotchas

**CSS `[hidden]` gotcha** (same issue as `diario-chamados`): setting `display` unconditionally on a class (e.g. `.modal-overlay { display: flex; }`) silently overrides the `[hidden]` attribute's built-in `display: none`, because author CSS wins over the user-agent stylesheet at equal specificity. Every element toggled via the `hidden` attribute here (`.modal-overlay`, `.toast`, `.sidebar-overlay`, `.step-detail`, `.scope-mini`, `.mobile-stepbar`, `.setup-blocker`, `.checklist-evidence`) has an explicit `.the-class[hidden] { display: none; }` rule — keep that pairing if you add another one. `.checklist-evidence` additionally gets a `@media print` override forcing it visible even when `hidden` (see Achados & Relatório) — the two rules don't conflict because print styles only apply inside that media query.

**Literal `</script>` inside content data breaks the page.** The HTML parser looks for the raw byte sequence `</script` anywhere inside a `<script>` element's text — including inside a JS string literal — and ends the script tag right there, regardless of quoting. This bit us once already: an example `code:` string containing a literal CSRF PoC (`<script>document.forms[0].submit()</script>`) truncated the entire app's script block. If a command/example/code string needs to contain `</script>`, split it so the raw bytes never form that exact sequence, e.g. `'<\/script>'` (the backslash is dropped by the JS string parser but prevents the HTML tokenizer from matching) or string concatenation like `'<scr' + 'ipt>'`.

**CSS custom property renames must cover the whole file, not just `<style>`.** Several render functions build inline `style="color:var(--x)"` strings in JS (e.g. `methodologyRowHTML`, `renderEngagementModal`). A file-wide token rename during v2 development initially only patched the `<style>` block via a scoped script and missed these JS-embedded references, leaving a few components pointing at now-undefined custom properties (silently invisible/default-colored, no console error). If you rename a `--token`, grep the whole file, not just between `<style>` and `</style>`.
